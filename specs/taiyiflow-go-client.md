# 太乙智启本地命令行（CLI）智能体客户端计划

## 1. 当前情况判断

当前仓库还处于规划阶段，只有规格文档，尚未进入实际编码。原文档主要围绕“对接某个后端服务应用程序编程接口（API）的 Go 客户端”展开，但这与当前目标已经不一致。

现阶段更符合实际的方向应当是：先打造一个本地优先的命令行（CLI）智能体客户端工具，并且把入口收敛到足够简单。它不再拆成“对话入口”“代码入口”“办公入口”三套命令，而是采用一个主入口，用自然语言统一处理代码、文档、脚本、排障和日常文本任务。

因此，这份计划不再把“某个固定服务端应用程序编程接口（API）的接入”作为唯一主题，而是调整为“本地命令行（CLI）智能体产品 + 可扩展执行框架”的落地方案。产品目标形态可以直接定义为：做一个中国的 Claude Code。

但需要明确的是，首版客户端不再完全抽象化处理后端来源，而是直接以 ../taiyiflow/src/backend/base 目录中的后台 stream 接口实现作为默认依赖基线。也就是说，客户端的首版联调、协议兼容、事件流处理和会话头约定，都以后端 base 目录中的真实实现为准。

## 2. 产品定位

太乙智启命令行（CLI）是一个运行在本地终端中的智能体客户端。它的核心价值不是单纯聊天，而是基于本地环境、工作目录、命令执行能力和文件处理能力，帮助用户完成真实任务。

它的目标形态不是通用聊天壳，也不是命令很多的工具箱，而是一个单入口、强执行、偏代码工作的本地智能体，使用体验尽量接近 Claude Code，但更适合中文用户和中国本地开发环境。

它应该具备以下产品特征：

- 本地优先：默认在本机运行，直接理解当前目录、文件、命令和用户上下文。
- 任务导向：以“完成任务”为目标，而不是只输出答案。
- 单一入口：对话、代码处理、文档整理走同一个入口，由智能体自己判断任务类型。
- 代码优先：核心能力先围绕开发工作建立，再自然外溢到文档和办公文本处理。
- 中文优先：更适配中文表达、中文文档、中文团队协作和国内模型生态。
- 后端对齐：首版直接依赖 ../taiyiflow/src/backend/base 中的流式接口实现，避免客户端协议层与服务端实际行为脱节。
- 模型可替换：支持本地模型、OpenAI 兼容接口、企业内部模型、太乙智启平台等多种后端。
- 可控执行：对命令执行、文件写入、外部访问设置权限边界与审批机制。
- 可扩展：后续可接入模型上下文协议（MCP）、插件、脚本包、企业知识库和办公系统。

## 3. 核心目标

### 3.1 总目标

做成一个真正可用的本地命令行（CLI）智能体工具，而不是一个只能演示问答的命令行壳。

### 3.2 产品形态目标

- 用一个主入口承接连续对话、代码修改、排障分析和文档整理
- 让用户更多地“说目标”，而不是记很多子命令
- 让智能体围绕当前工作目录自主决定是否读文件、执行命令、生成补丁和总结结果
- 在单次任务和连续会话之间自然切换，而不是拆成多套交互模型

### 3.3 任务能力目标

- 理解当前代码仓库结构和上下文
- 进行代码问答、修改建议、重构建议和问题定位
- 协助生成代码、测试、脚本、文档和提交说明
- 总结本地文档、会议纪要、方案材料和日报周报内容
- 起草邮件、通知、汇报、方案初稿、流程说明
- 通过受控命令执行完成构建、测试、搜索和验证

### 3.4 本土化目标

- 更好支持中文需求描述和中文输出风格
- 适配国内常见模型接入方式和企业网络环境
- 更贴近中国团队常见的研发、汇报和文档协作习惯

## 4. 非目标

为了保证首期可落地，以下内容不作为第一阶段目标：

- 不做图形界面，先专注命令行（CLI）体验
- 不做完整多端同步体系
- 不一次性接入所有办公系统
- 不强绑定某一个模型平台或某一个后端协议
- 不把复杂多智能体编排作为首期重点
- 不在第一阶段承诺完全自动化的高风险操作
- 不做一套命令对应一个场景的复杂命令树

补充说明：虽然长期仍保留“模型提供方（Provider）抽象”的演进方向，但首版实现将优先强依赖太乙智启后台 stream 接口，不以完全通用化为先。

## 5. 用户与场景

### 5.1 目标用户

- 经常在终端里工作的开发者
- 需要同时处理代码、文档和汇报材料的技术负责人
- 希望用一个命令行（CLI）工具承接大部分知识工作流的高级个人用户

### 5.2 典型编程任务

- 在当前仓库中搜索并解释某个模块
- 根据需求生成代码改动方案并落地修改
- 执行测试、读取错误输出并辅助修复
- 为某个需求生成脚手架、配置文件和文档
- 对已有改动做代码审查（review）、总结风险和补充测试建议

### 5.3 典型文档任务

- 总结长文档并提炼重点
- 把会议纪要整理成行动项和责任人清单
- 把零散素材整理成周报、汇报稿或方案初稿
- 按模板生成邮件、通知、公文风格文本
- 对目录中的材料进行分类、命名建议和摘要生成

## 6. 产品原则

### 6.1 本地优先

默认围绕本地目录、本地文件和本机命令运行。用户在什么目录下启动命令行（CLI），智能体就优先理解那个目录的上下文。

### 6.2 人在回路

涉及写文件、执行命令、删除内容、访问外部服务等动作时，需要提供清晰的预览与确认机制。默认不做高风险静默执行。

### 6.3 任务闭环

不是只返回一段文本，而是尽可能完成“分析 -> 执行 -> 验证 -> 总结”的闭环。

### 6.4 模型解耦

命令行（CLI）本身在架构上应尽量独立于模型提供方。模型能力通过模型提供方（Provider）抽象接入，避免后续切换成本过高。

但在首版落地上，不追求先做完全通用的后端抽象层，而是先对齐 ../taiyiflow/src/backend/base 中已经存在的后台 stream 接口实现。也就是说，抽象保留，默认实现先绑定太乙智启后台基线。

### 6.5 场景渐进

先把最常用、最高频、最容易验证价值的任务做好，再扩展复杂自动化能力。

### 6.6 入口收敛

尽量不让用户记忆很多命令。主入口解决大部分事情，只有配置、诊断、版本等少数能力保留辅助命令。

## 7. 首期能力范围

### 7.1 最小化可行产品（MVP）能力

1. 单一主入口的任务执行
2. 本地文件读取、目录检索、写文件与补丁应用
3. 受控命令外壳（Shell）命令执行
4. 会话（Session）上下文保存与恢复
5. 面向代码仓库的基本感知能力
6. 面向文档材料的总结与起草能力
7. 配置管理和模型提供方（Provider）切换能力
8. 与 ../taiyiflow/src/backend/base 后台 stream 接口的协议兼容能力
9. 本地技能(skill)发现、查看、启停与透传能力
10. 工作目录访问边界、敏感路径拒绝、审计日志与审批模式联动

### 7.2 当前已落地能力

截至当前仓库实现，客户端已经具备以下能力基线：

1. 本地客户端工具注册已覆盖 search_files、glob_files、read_file、write_file、file_edit、shell_exec、task_list、task_output、task_stop、task_delete、terminal_capture、todo_write、lsp_query、skill。
2. 文件工具默认受工作目录访问边界限制，可附加 sandbox_roots 扩展额外外部资源访问根目录。
3. 敏感目录（如 ~/.ssh、~/.gnupg、~/.aws、macOS Keychains）默认拒绝访问。
4. 写文件、细粒度编辑、Todo 更新和任务停止操作统一遵循 approval_mode；只读模式会直接拒绝执行。
5. 命令执行会剔除常见敏感环境变量，并对高风险命令在 auto 模式下阻断。
6. 客户端支持 ~/.snz1dp/skills 目录下的 SKILL.md 发现与透传；运行时的 skill 工具已收窄为按名称装载单个技能提示内容(prompt)的执行入口。
7. TUI 与交互模式均提供 /skills 命令；doctor 会输出文件工具链和技能目录状态。
8. TUI 状态栏已支持窄终端分级压缩，并将本地工具与命令执行摘要收敛到状态栏和关键里程碑消息；Todo、后台任务输出与 lsp_query 结果会进入专门的工具结果面板。
9. shell_exec 已复用现有命令执行内核正式化为客户端工具，并补齐后台任务句柄(task handle)、输出读取、终端捕获、停止与删除能力。
10. Todo 清单已保存到当前会话状态，后台任务 metadata 与 stdout/stderr 会持久化到 `SNZ1DP_HOME/tasks/`；CLI 重启后仍可继续查看、捕获或删除已恢复任务。
11. lsp_query 通过本地标准输入输出(stdio)语言服务器(language server)提供定义跳转(go_to_definition)、引用查询(find_references)、实现跳转(go_to_implementation)、文档符号(document_symbol)、工作区符号(workspace_symbol)五类查询；当前不需要扩展太乙智启后台 stream 协议。
12. 交互式 CLI 与 TUI 已接入 `/review`、`/tasks`、`/permissions`、`/skills` 等本地工作流命令，其中 `/tasks` 已支持 `list`、`output`、`capture`、`stop`、`remove`。

### 7.3 第二阶段增强

1. 补丁级代码修改与文件变更预览
2. Git 版本控制工作流支持
3. 模板化办公任务
4. 插件机制或模型上下文协议（MCP）接入
5. 多工具链协作和更强的计划执行能力

### 7.4 后续扩展

1. 企业知识库接入
2. 邮件、日历、IM、文档平台连接器
3. 更复杂的多智能体协作
4. 团队级配置、审计与策略控制

## 8. 功能模块设计

### 8.1 命令行（CLI）交互层

负责命令解析、交互式会话、参数处理和输出展示。

交互方式应当尽量像 Claude Code 一样收敛：

1. 不带参数启动时，进入连续会话模式
2. 带一句自然语言启动时，执行单次任务模式
3. 配置、自检、版本等保留少量辅助命令

建议命令结构：

```text
taiyiflow [task]
taiyiflow --continue
taiyiflow --new "修复当前测试失败"
taiyiflow config
taiyiflow skills list
taiyiflow doctor
taiyiflow version
```

建议的会话内斜杠命令：

- /help
- /clear
- /review
- /tasks
- /permissions
- /skills
- /diff
- /approve
- /exit

### 8.2 智能体运行时（Agent Runtime）

负责计划拆解、上下文组织、模型调用、工具调度和结果汇总。

这里建议不要一开始就做复杂编排，而是先实现一个稳定的单智能体执行框架，具备以下能力：

- 接收用户目标
- 维护当前任务状态
- 决定是否需要读文件、执行命令、改写内容
- 汇总执行结果并继续下一步
- 在达到条件时结束任务

### 8.3 上下文（Context）管理

需要解决命令行（CLI）智能体最核心的问题：如何正确理解当前任务上下文。

建议至少包含以下上下文源：

- 当前工作目录
- 用户输入
- 最近会话历史
- 选定文件内容
- 目录结构摘要
- 命令执行结果
- 任务过程中产生的临时计划

### 8.4 工具（Tool）执行层

首期工具应聚焦本地能力，不要一开始就追求全连接。

首期建议内置工具：

- 文件工具：read_file 读文件、glob_files 枚举、search_files 搜索内容、write_file 写文件、file_edit 细粒度替换；其中 file_edit 在 PATCH_CONFLICT 时返回 prefetched_read 与 retry_hint，供后续安全复用
- 命令外壳(shell)工具：执行构建、测试、脚本、查询命令，并支持后台任务输出读取与停止
- 任务工具：会话级 Todo 清单读写、后台任务列表查询
- 代码语义工具：通过本地语言服务器(language server)执行 lsp_query
- skill 工具：按名称装载单个技能提示内容(prompt)，执行入口与 /skills 管理命令分离
- 文档工具：提取 Markdown、纯文本（TXT）、逗号分隔值（CSV）、JSON 等内容

首期工具治理要求：

1. 默认工作目录为基础访问根目录，支持通过 sandbox_roots 配置额外白名单路径。
2. 写文件、补丁、技能启停等本地变更操作统一接入 approval_mode。
3. 审计日志默认写入 ~/.snz1dp/logs/audit.log，可通过 audit_enabled 开关控制。
4. 本地技能目录默认使用 ~/.snz1dp/skills，技能文件采用 SKILL.md（YAML frontmatter + Markdown body）。
5. 通用客户端工具通过 client_mcp_servers 透传即可被后台消费；本轮新增 shell_exec、Todo、lsp_query、file_edit、Task 工具不需要额外扩展 stream 事件或回调 schema。

第二阶段可补充：

- 便携式文档格式（PDF）、Word 文档（DOCX）、Excel 工作簿（XLSX）解析
- 模板生成器
- 邮件和 IM 连接器
- 模型上下文协议（MCP）工具接入

### 8.5 后台 stream 接口依赖

首版客户端默认依赖 sibling 目录 ../taiyiflow/src/backend/base 中的后台实现，尤其是以下文件和接口约定：

- taiyiflow/api/v1/endpoints.py
  - 负责核心流式端点 POST /api/v1/run/{flow_id_or_name}/stream，以及辅助端点 GET /api/v1/run/{flow_id_or_name}/metadata。
  - 获取默认的流程服务（default_flow_id）、欢迎语、功能列表、智能体选项等元信息的接口也需要对齐。
- taiyiflow/api/v1/schemas.py
  负责请求与事件流结构定义，客户端首版至少需要对齐 SimplifiedAPIRequest、RunResponse、StreamData 等结构。
- taiyiflow/processing/process.py
  负责事件流产生逻辑，客户端需要按其真实行为处理 message、error、close 三类事件，并兼容 chunk、message、error、type 等数据字段。
- taiyiflow/utils/constants.py
  负责会话请求头常量定义，客户端需要读取 X-TaiyiFlow-Session-id 响应头并据此恢复会话。
- taiyiflow/api/v1/agent_chat.py
  提供 agents/flows、xsessions 等辅助接口，用于主入口之外的元数据查询、智能体列表和会话管理。

首版协议兼容要求：

1. 客户端必须支持 text/event-stream 响应。
2. 客户端必须支持标准服务器发送事件（SSE）格式的 event/data 分帧。
3. 客户端必须正确处理 message、error、close 三类事件。
4. 客户端必须读取 X-TaiyiFlow-Session-id 响应头。
5. 客户端在开发与联调阶段，以 ../taiyiflow/src/backend/base 的代码实现作为真值来源，而不是自定义一套独立协议。

### 8.6 模型提供方（Provider）抽象层

模型接入层建议抽象为统一接口，避免命令行（CLI）逻辑直接耦合具体厂商。

建议支持的模型提供方（Provider）类型：

- 本地模型：如 Ollama
- OpenAI 兼容接口
- 企业内部模型网关
- 太乙智启平台能力接入

但在实现优先级上，首版只需要把太乙智启平台对应的后台 stream 接口接稳，不要求同时把其他模型提供方（Provider）做完整。

### 8.7 输出呈现层

终端输出不应只是原始文本堆叠，需要具备基础可读性：

- 区分用户输入、模型回复、执行日志、错误信息
- 对代码块、命令块、表格和列表做友好展示
- 在长任务中展示当前阶段和进度
- 在执行前展示拟执行动作，在执行后给出结果摘要

## 9. 统一任务入口设计

核心原则是同一个入口处理“问答、代码、文档、脚本、总结”。用户不需要先判断这是代码任务还是办公任务，智能体应当根据上下文和工具能力自动选择执行方式。

典型输入示例：

```text
taiyiflow "解释这个仓库的启动流程"
taiyiflow "修复当前测试失败，并解释根因"
taiyiflow "根据 git 差异（diff）生成一段中文提交说明"
taiyiflow "把 docs/方案.md 总结成 5 条汇报要点"
taiyiflow "整理 notes/meeting.txt，输出行动项和责任人"
```

对用户来说，这些都是一句自然语言；对系统来说，区别只是背后使用了不同的上下文、工具和输出模板。

## 10. 代码优先，文档同入口

这个产品的核心仍然是代码工作，而不是泛办公助手。更准确的说法是：先把“代码型智能体”做强，再让它通过同一个入口顺手处理开发过程中的文档和文本工作。

首期重点任务：

1. 仓库检索和问答
2. 文件级修改建议或补丁输出
3. 测试执行与错误解释
4. Git 差异（diff）总结和提交说明生成
5. 方案、周报、会议纪要等文本整理

这意味着不会再拆出单独的 office 命令，而是把文档处理视为主入口能力的一部分。

## 11. 技术实现建议

结合当前文件名和后续作为命令行（CLI）分发工具的需求，建议继续使用 Go 实现首版客户端。

原因如下：

- 适合做单二进制命令行（CLI）分发
- 启动快，适合本地工具常驻使用
- 并发处理流式输出、命令执行和会话管理比较直接
- 对跨平台发布友好
- 适合对接现有 Python 后端的 HTTP stream 接口，而不需要在客户端引入 Python 运行时

```text
taiyiflow-cli/

├── go.mod
├── cmd/
│   ├── root.go
│   ├── config.go
│   ├── doctor.go
│   └── version.go
├── internal/
```

### 11.2 核心抽象建议

- 智能体运行时（AgentRuntime）：负责任务执行主循环
- 模型提供方（Provider）：负责与模型后端通信
- 工具（Tool）：负责本地工具调用
- 会话存储（SessionStore）：负责会话持久化
- 安全策略（SafetyPolicy）：负责命令、写入、网络访问的策略控制

### 11.3 首版后台依赖实现建议

首版建议在 internal/provider/taiyiflow/ 下实现太乙智启专用适配层，职责如下：

1. 组装发送到 /api/v1/run/{flow_id_or_name}/stream 的请求体。
2. 解析服务器发送事件（SSE）流并映射为客户端内部事件。
3. 读取 X-TaiyiFlow-Session-id 响应头并维护本地会话。
4. 调用 /api/v1/run/{flow_id_or_name}/metadata 获取欢迎语、功能和基础元信息。
5. 调用 /api/v1/agents/flows 等辅助接口完成智能体选择与会话恢复。

开发期约束：

- 接口行为以后端源码 ../taiyiflow/src/backend/base/taiyiflow/api/v1/endpoints.py 为准。
- 事件结构以后端源码 ../taiyiflow/src/backend/base/taiyiflow/api/v1/schemas.py 为准。
- 关闭事件与错误语义以后端源码 ../taiyiflow/src/backend/base/taiyiflow/processing/process.py 为准。

## 13. 安全与边界控制

这是本地智能体和普通聊天工具最大的区别，必须提前设计。

### 13.1 高风险动作

- 删除文件
- 覆盖关键配置
- 执行命令外壳（Shell）写操作
- 访问外部网络
- 提交 Git 变更

### 13.2 控制策略

- 默认显示即将执行的动作
- 对危险命令做拦截或二次确认
- 对敏感信息做脱敏展示
- 保留关键操作日志
- 明确区分“建议执行”和“已执行”

## 15. 首期开发优先级

建议按以下顺序推进，而不是平均铺开：

1. 命令行（CLI）工程骨架
2. 模型提供方（Provider）抽象 + 一个可用模型接入
3. 文件工具 + 命令外壳（Shell）工具
4. 单一主入口命令
5. 会话与上下文管理
6. 太乙智启后台 stream 接口适配
7. 代码场景最小化可行产品（MVP）
8. 文档场景最小化可行产品（MVP）

这个顺序的原因很直接：先做通用底座，再做最高频场景，避免过早陷入办公连接器或复杂自动化细节。

## 16. 验收标准

当首个可发布版本具备以下能力时，可以认为方向成立：

1. 用户可以在任意本地目录通过同一入口启动命令行（CLI）并进行连续任务对话
2. 工具可以读取文件、搜索内容、执行受控命令并返回结果
3. 工具可以辅助处理常见代码任务
4. 工具可以通过同一入口辅助处理常见文档和汇报任务
5. 会话、配置、审批机制可正常工作
6. 模型提供方（Provider）可替换，不依赖单一后端

补充说明：以上第 6 条属于架构演进目标，不要求首版先于太乙智启后台依赖解耦完成。

## 17. 后续与太乙智启平台的关系

这项计划并不排斥太乙智启平台，反而给它留出了更合理的位置。

更合适的策略是：

- 首版命令行（CLI）主体直接依赖 ../taiyiflow/src/backend/base 中已经存在的后台 stream 接口实现
- 客户端通过 internal/provider/taiyiflow/ 适配层对齐服务端协议与事件流行为
- 在首版稳定后，再向更通用的模型提供方（Provider）抽象演进

这样做的好处是：

1. 首期联调对象明确，客户端协议实现不会漂移
2. 本地使用体验更直接，验证价值更快
3. 后续再做抽象时，基线行为已经有真实后端支撑

## 18. 结论

基于当前实际情况，这个项目应当从“通用后端应用程序编程接口（API）客户端”调整为“单入口、本地优先、并默认依赖太乙智启后台 stream 实现的代码型命令行（CLI）智能体客户端”。

第一优先级不是穷举服务端接口，也不是设计一棵复杂命令树，而是尽快做出一个像 Claude Code 一样可直接进入工作流的命令行（CLI）原型。这个原型在首版阶段直接依赖 ../taiyiflow/src/backend/base 的后台 stream 接口实现，以代码任务为核心，通过同一入口顺带处理文档和中文协作任务；等这个方向跑通之后，再向更通用的模型提供方（Provider）抽象演进，会更符合产品落地和工程推进逻辑。
