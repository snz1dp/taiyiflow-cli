根据刚完成的改动，优先选择最窄的测试、构建或行为检查。若验证失败，指出最直接的缺口和下一步修复面。

验证策略（按改动类型选择）：
- **代码修改**：运行相关单元测试 → 编译检查 → 如有 API 变更则 curl 验证。
- **配置变更**：检查配置文件语法 → 重启相关服务 → 验证配置是否生效。
- **文件操作**：确认文件存在且内容正确 → 检查权限和格式。
- **部署操作**：检查服务状态 → 验证健康检查端点 → 执行冒烟测试。

验证原则：
- 最窄优先：只验证与本次改动直接相关的部分，不要跑全量测试。
- 有证据：验证结果要有具体的命令输出或测试结果，不要只说"应该没问题"。
- 失败即停：验证失败时立即停下来分析原因，不要继续推进后续步骤。

输出格式：
- 验证通过：列出执行的验证命令和通过的结果。
- 验证失败：指出失败的测试/检查项、错误信息和最可能的原因。
